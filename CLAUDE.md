# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Physical inventory ("Inventario Físico de Bienes y Enseres") web app for a church (Iglesia Cristiana de Avivamiento – Tiempo de Restauración, sede CERES). The UI, code identifiers, and comments are in **Spanish**; keep new code consistent with that. It replaces a paper/Excel form, and the report screen must keep matching that form's layout.

Stack: Vite 8 + React 19 + TypeScript 6 + Tailwind CSS v4 (CSS-first config, no `tailwind.config.js`) + Supabase (Postgres + Auth). Deployed on Vercel (`vercel.json` holds the SPA rewrite to `index.html`).

Auth is Supabase email/password with open self sign-up (`/crear-cuenta`, email confirmation required). The sign-up sends `nombre`, `apellido` and `lugar_id` as user metadata, and the `crear_perfil()` trigger copies them into `public.perfiles` (`0003`, redefined in `0004`; an invalid `lugar_id` is stored as NULL so sign-up never fails).

**Sede vs lugar naming**: the UI calls them "sedes", but the DB keeps the original names: table `lugares` and columns `perfiles.lugar_id` and `bienes.lugar_id`. The user asked for the rename to be front-end only, so do not rename DB objects. `src/lib/sedes.ts` maps the `Sede` type onto `lugares`. `anon` can read active `lugares` rows (RLS), because the sede select is shown before login.

**Inventory is per sede**: the user picks a sede at login (also at sign-up, and later from the top-bar "Cambiar" dialog). `AuthProvider` holds it as `sedeActiva`, persisted in localStorage (`inventario.sedeActiva`). `RequireAuth` shows an "Elige la sede" screen if there is a session but no sede. Inside protected routes, `useSedeActiva()` always returns a `Sede`. `useBienes()` filters by `lugar_id` and its query key includes the sede id. New bienes get `lugar_id` and `lugar` (the name, a denormalized text copy) from the active sede, while edits keep the bien's own sede. Listado and Reporte are keyed by sede id so their filters reset when the sede changes. Since `0017`, only the Administrador may choose any sede; every other role is locked to its profile's sede (see **Permisos por rol**).

**Ubicaciones** (`0006`, made per sede by `0010`): each row in `ubicaciones` belongs to one sede (`lugar_id`), and only `authenticated` can read the table. Names are unique within a sede, not globally. A bien stores `ubicacion_id` (nullable for legacy rows) and `ubicacion` (the description, a denormalized text copy written on save). A composite FK `(ubicacion_id, lugar_id) → ubicaciones(id, lugar_id)` guarantees that a bien's ubicación belongs to the bien's own sede. `useUbicaciones(sedeId)` lists one sede's active rows: the active sede for a new bien, the bien's own sede when editing. Listado and Reporte filters, the Dashboard KPI and the report read the text copy. `Registro.tsx` waits for the list to load before mounting the form, so the uncontrolled `<select>` shows the saved value.

## Commands

- `npm run dev`: dev server at http://localhost:5173
- `npm run build`: `tsc -b` type check, then Vite build (this is the type-check step; there is no separate one)
- `npm run lint`: oxlint (`.oxlintrc.json`)
- No test runner is configured.

Setup needs a `.env` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (see `.env.example`). Without it, the app still renders, `supabase` is `null`, and the login page shows a warning. The DB schema is in `supabase/migrations/`, applied in order by hand in the Supabase SQL editor (there is no Supabase CLI). Sample data is in `supabase/seed/`; it is not idempotent, so running it twice duplicates rows.

Deploy: `npx vercel --prod`. The `VITE_*` variables must also be set in Vercel's project settings, because they are inlined at build time.

## Architecture

- **Data layer, `src/lib/bienes.ts`**: the single module that talks to Supabase. It holds the `Bien` type, the CRUD functions, the React Query hooks (`useBienes`, `useBien`, `useGuardarBien`, `useEliminarBien`) and derived calculations (`resumen`, `valorTotal`, `ubicacionesDe`). Every screen reads the **whole** `bienes` list through one shared query key (`['bienes']`) and filters, paginates and totals on the client. Mutations invalidate that key. Postgres `numeric` comes back as a string, so rows go through `normalizar()`.
- **Report format, `src/lib/reporte.ts`**: the single source of truth for the report layout, which the user matched to a reference screenshot. It defines the three-box header (`IGLESIA`), the 16 columns A–P in Excel order (`COLUMNAS`), `filaReporte()` (one row, with ESTADO split into B/R/M columns marked "✓"), the "TOTALES (n bienes)" row and the three signature blocks (`FIRMAS`: Elaborado, Revisado, Aprobado por). There are no padding rows. The report always covers the whole active sede (no filters), and only the date is editable, inline in the header. Two renderers consume it:
  - `HojaInventario` in `src/pages/bienes/Reporte.tsx`: the on-screen and print view (`window.print()`).
  - `src/lib/exportExcel.ts`: builds the `.xlsx` with exceljs. `construirExcel()` returns the buffer and `exportarExcel()` downloads it. exceljs is loaded with a dynamic `import()` so it stays out of the main bundle (that is why `chunkSizeWarningLimit` is raised in `vite.config.ts`).
  When a field or column changes, update the SQL migration, `Bien`, the form schema in `Registro.tsx`, and `reporte.ts`. Both renderers then follow.
- **Printing**: `.no-print` hides app chrome, and `.print-area` plus the `@media print` rules in `src/index.css` set A4 landscape and repeat the table header on every page.
- **UI kit, `src/components/ui/`**: small hand-written, shadcn-style components (not the shadcn CLI). Theme colors (`primary`, `bueno`, `regular`, `malo`, …) are Tailwind v4 `@theme` tokens in `src/index.css`. Non-component exports live in separate `.ts` files (`button-variants.ts`, `toast-context.ts`) so oxlint's `only-export-components` rule passes.
- **Auth**: `AuthProvider` (`src/components/AuthProvider.tsx`) holds the session and exposes it through `useAuth()` from `src/lib/auth-context.ts`. A `session` of `undefined` means it is still loading, and `null` means logged out. `RequireAuth` wraps every route except `/login`, `/crear-cuenta` and `/confirmar-correo`. Logging out clears the React Query cache. Supabase error codes are translated to Spanish in `ERRORES` (`src/lib/auth-errores.ts`). Sign-ups send `emailRedirectTo: urlConfirmacion()` (`${origin}/confirmar-correo`). The Supabase "Confirm signup" email template is customized to link to `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=email`, so that origin must be listed in Supabase's *Redirect URLs* (otherwise Supabase falls back to the *Site URL*). `ConfirmarCorreo.tsx` calls `verifyOtp` only when the user clicks the button, because mail link scanners (Outlook Safe Links) would otherwise spend the one-time token. On success it signs out, so the user logs in normally and picks a sede. On error it offers `auth.resend`.
- **Routing, `src/App.tsx`**: `/login` and `/crear-cuenta` are public. The protected routes are `/` dashboard, `/bienes` list, `/bienes/nuevo` and `/bienes/:id` share `Registro.tsx` (the form is keyed by id so it remounts with fresh defaults), and `/reporte` is the report.
- **Forms**: react-hook-form + zod 4 through `@hookform/resolvers` v5 (v6 has a peer-dependency conflict). Number inputs use `valueAsNumber`. Empty optional strings become `null` before saving (`aInput`).

## Conventions

- Currency is PEN: use `formatMoneda()` (`es-PE`). Dates are stored as ISO `date`, and `formatFecha()` shows them as dd/mm/yyyy without timezone conversion.
- Asset state is the enum `'B' | 'R' | 'M'` (Bueno/Regular/Malo). Display it with `EstadoBadge`.
- Unit of measure (`bienes.unidad_medida`) stores the `codigo` of a row of the `unidades_medida` catalog (`0018`, epic in `docs/pendientes/epica-unidades-medida.md`): 17 units in 4 `tipo` groups (Cantidades y agrupaciones, Peso, Volumen y capacidad, Longitud y superficie), global like `categorias` (read: authenticated, write: Administrador). Configuración → Unidades de medida (`src/pages/configuracion/UnidadesMedida.tsx`, hooks in `src/lib/unidades.ts`) manages it; `codigo` is read-only when editing, and a unit in use by a bien cannot be deleted (checked in `useEliminarUnidad`, there is no FK), only deactivated. The bien form combo shows the active units in `optgroup`s, and `Registro.tsx` waits for the list before mounting. The DB column stays plain text with no FK, so a saved value that is inactive or outside the catalog is kept as an extra option when editing. `opcionesCon()` (`utils.ts`) does the same for the ubigeo selects.
- Searchable combos: `Combobox` (`src/components/ui/combobox.tsx`) filters while typing, ignoring case and accents (`normalizarTexto()` in `utils.ts`). The bien form uses it for Categoría, Unidad de medida (grouped by tipo) and Ubicación through react-hook-form `Controller`; the other selects stay native.
- Import from `src/` through the `@/` alias.

**Usuarios y roles** (`0007`): a user is a `perfiles` row (with `telefono` and `rol_id` → `roles`) tied to a Supabase Auth account, and any authenticated user can read and update every profile. Roles grant permissions since `0017` (see **Permisos por rol**). "Usuarios → Registro" cannot create Auth users directly, because that needs the service_role key, which must never reach the frontend. Instead it calls `signUp` through `clienteSinSesion()` (`src/lib/supabase.ts`), a client that does not persist a session, so the admin stays logged in. The new user then gets the confirmation email. Profile data travels as signUp metadata and the `crear_perfil()` trigger stores it. Email is read-only when editing a user.

**Sexo, función, foto y eliminación de usuarios** (`0011`): `perfiles` gains `sexo` (`'M' | 'F'`), `funcion` (`'Pastor' | 'Siervo' | 'Diácono'`, a fixed list in `FUNCIONES`, separate from the `roles` table) and `foto`, which is the object path in the private Storage bucket `usuarios` (`<user_id>/<uuid>.<ext>`). The bucket's policies mirror `bienes`. `imagenes.ts` and `CampoImagen` take a `bucket` parameter that defaults to `'bienes'`. On create, the photo is uploaded after `signUp` returns the new id and is then saved with an update.

**Roles del sistema** (`0012`): the `roles` rows are Administrador, Encargado, Revisor and Aprobador (they replaced Pastor/Siervos/Diáconos, whose values moved to `perfiles.funcion`). Permissions came with `0017`. All pending features and manual setup tasks are tracked in `docs/BACKLOG.md`; keep it updated when you finish or discover pending work. `crear_perfil()` no longer copies `rol_id` from sign-up metadata, because public sign-up has no session and anyone could otherwise pick Administrador. "Usuarios → Registro" sets the role with an update right after `signUp`, in the same step as the photo. Deleting a user calls the `security definer` RPC `eliminar_usuario(p_id)`, which deletes from `auth.users` (the profile cascades) and refuses to delete the caller. The frontend then deletes the photo. The "Eliminar usuario" button appears when editing and, since 28/10/2026, also as a trash icon in Usuarios → Listado (`eliminarUsuarios`, so Administrador only; disabled on your own row).

**Permisos por rol** (`0017`): `roles.codigo` is fixed (`admin`, `encargado`, `revisor`, `aprobador`) and the app neither creates nor renames roles (Usuarios → Roles is a read-only list). Only the Administrador reaches every sede and everything else; any other role sees only the sede in its own `perfiles.lugar_id`. Encargado: bienes and ubicaciones of its sede (read and write), and list/create/edit of users of its sede (never an Administrador, no delete). Revisor and Aprobador: read-only for their sede (Panel, Listado, Reporte). Categorías, Sedes and Roles are Administrador-only (everyone can read categorías and sedes); `eliminar_usuario()` requires the Administrador. A profile without a role sees the "pendiente de aprobación" screen (also a non-admin without a sede). Enforcement is RLS (helpers `rol_actual()`, `sede_propia()`, `es_admin()`, `es_rol_admin()`, also on the Storage policies, whose first path folder is the sede id for `bienes` and the user id for `usuarios`). The UI only mirrors it: `usePerfilActual()`/`usePermisos()` in `src/lib/permisos.ts`, menu filtering in `SidebarNav`, route guards with `RequierePermiso` in `App.tsx`, and `RequireAuth`, which forces `sedeActiva` to the profile's sede for non-admins (the sede picked at login is ignored; "Cambiar" is hidden). `bienes/:id` needs edit permission, so Revisor/Aprobador have no detail view. The migration aborts if no Administrador remains: it assigns it by email (edit the list in step 2 before running).

**Etiquetas QR** (epic in `docs/pendientes/epica#6-etiquetas-qr.md`, phase 1; no DB changes): the QR is never stored, it is drawn in the browser from `bienes.id` and encodes `${origin}/bienes/<id>` (`src/lib/etiquetas.ts`: `textoQr`, `idDesdeTexto`, `qrSvg`, which loads `qrcode` with a dynamic `import()`). `Etiquetas.tsx` (`/bienes/etiquetas`, needs `editarBienes`; preselects with `?ids=1,2,3`) prints A4 portrait sheets of 2×5 `EtiquetaBien` (QR 44 mm), one label per unit (copies default to `cantidad`); it injects its own `@page` so the A4 landscape of the report is untouched. `Escanear.tsx` (`/escanear`, every role) reads with the camera (`@zxing/browser`, dynamically imported, needs HTTPS) or a keyboard-style USB/Bluetooth reader, and looks the bien up in `useBienes()`, so a bien from another sede is "not found". `/bienes/:id` goes through `BienPorId.tsx`: users who can edit get the form, the others are redirected to `/escanear?bien=<id>` (read-only card). Phase 2 (conteo físico, migration `0018`) is pending.

**Imagen de bienes** (`0008`): photos live in the private Storage bucket `bienes` (5 MB limit, image MIME types only, `authenticated`-only policies). `bienes.imagen` stores just the object path (`<lugar_id>/<uuid>.<ext>`). The UI shows images through 1-hour signed URLs (`useUrlImagen`, `src/lib/imagenes.ts`), and only in the Registrar/Editar bien form (`CampoImagen`); by request they never appear in the Listado or the reports. On save, a new image is uploaded first and deleted again if the save fails, and a replaced or removed image is deleted afterwards. `eliminarBien` also deletes the image. The form no longer shows a Sede field: new bienes still get the active sede.

**Configuración → Sedes / Ubicaciones** (`0009`): Ubicaciones uses the generic page `CatalogoPage` (`src/components/CatalogoPage.tsx`) with `src/lib/catalogos.ts`, where a `ConfigCatalogo` gives the table, its name column and the query keys to invalidate. Sedes has its own page and dialog form (`src/pages/configuracion/Sedes.tsx`, hooks `useSedesDetalle`, `useSede`, `useGuardarSede` and `useEliminarSede` in `src/lib/sedes.ts`), because since `0013` a sede also has `codigo` (unique, 2–10 of `A-Z0-9-`), `tipo` (required: Templo, Anexo or Casa de oración), `direccion`, `distrito`, `provincia`, `departamento` and `responsable_id` (→ `perfiles`). By request, the form does not show `codigo` or `orden` (they stay in the DB): editing never changes them, and a new sede gets the next `orden`. `departamento`, `provincia` and `distrito` are cascading selects fed by `src/lib/ubigeo-peru.json` (INEI ubigeo, uppercase without accents, generated from github.com/jmcastagnetto/ubigeo-peru-aumentado), loaded with a dynamic `import()` through `useUbigeo()` (`src/lib/ubigeo.ts`). They are still stored as text, and `opcionesCon()` (`utils.ts`) keeps a saved value that is not in the list. The `Sede` type used by login and the active sede is still just `{ id, nombre }`. `anon` can only select `id, nombre, orden, activo` (column grant), so the address and the responsable are not public. `lugares` and `perfiles` are now related twice, so embeds must name the FK (`lugares!perfiles_lugar_id_fkey`, `perfiles!lugares_responsable_id_fkey`).

**Categorías** (`0014`): `categorias` is a global catalog (not per sede, `authenticated` only) with `nombre` (unique), `prefijo` (unique, 2–5 letters), `tipo` (labeled "Tipo contable": `'Activo Fijo' | 'Suministro'` or null, `TIPOS_CONTABLES`, enforced by a check since `0015`), `descripcion` and `activo` (a default `unidad_medida` existed in `0014` and was dropped by request in `0016`). It has its own page and dialog (`src/pages/configuracion/Categorias.tsx`, hooks in `src/lib/categorias.ts`). `bienes.categoria_id` is optional. In the bien form, picking a category fills an empty `codigo_clasificacion` with the next `PREFIJO-NNN` among the active sede's bienes (`siguienteCodigo()`). The bienes Listado filters by category. The report does not show the category, because it must keep matching the paper form. A category in use cannot be deleted (23503), only deactivated.

**Report header district** (`0013`): the report header shows the sede's `distrito` (`distritoEncabezado()` in `reporte.ts`), falling back to `IGLESIA.distrito` (VITARTE). Authenticated users can read inactive rows and write; `anon` still sees only active sedes, and the combos query `activo = true` explicitly. Renaming a sede or ubicación updates the denormalized copies (`bienes.lugar`, `bienes.ubicacion`) through triggers. Catalogs with `porSede: true` (ubicaciones) list and create rows for the `sedeId` passed to the page; the Ubicaciones page passes the active sede and is keyed by it. A row in use cannot be deleted (FK error 23503), so the UI offers deactivating it instead.
